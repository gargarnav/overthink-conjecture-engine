# Methodology

These rules govern every result this project reports. If a result breaks one of them, it doesn't count.

## 1. Conjecture lifecycle

Every conjecture in the registry is in exactly one of these states:

| Status | Meaning |
|---|---|
| `proposed` | Generated by a miner or the LLM proposer; only checked on the data it came from. |
| `survived` | Re-tested on instances at least 10× larger than the proposal data, with no counterexample. **This is evidence, not proof.** |
| `refuted` | At least one counterexample was found and stored. Refuted conjectures stay in the registry permanently, and a later test can never change this status. |
| `untestable` | The falsifier could not test it: the sequence is missing at full scale, or has no new terms there. |
| `known` | Matches a statement in the literature or OEIS; the source is recorded. |
| `proved` | Has a Lean proof that compiles. The proof method is recorded (see §3). |

Status changes are appended to the registry (`registry/events.jsonl`) as events and never overwritten; the current status comes from replaying the events.

**Falsification rule.** A candidate applies to the sequence it was mined from and to every sequence that was identical to it in the proposal window (its aliases). It is `refuted` if it fails on any of them, and `survived` if it holds on all of them. A first-order sequence must also have new terms at full scale to count as `survived`. For second-order statements, the parameters are re-estimated with the same frozen miners on the full data and the statement is checked against those. When a candidate is refuted, the miners re-propose on the full sequence; those re-proposals are new conjectures, labelled unfalsified.

## 2. Provenance

Every conjecture records: dataset ID + content hash, the generating method and its parameters, the model and prompt hash (if an LLM was involved), the random seed, the git commit SHA, and UTC timestamps for each status change.

## 3. Proof labels

A "proof" is labelled by the method Lean used:

- `general`: a proof for all n, checked by the Lean kernel.
- `decide`: a finite statement checked by kernel evaluation (`decide`). Valid only for the stated finite range.
- `native_decide`: a finite statement checked by compiled code. This also trusts the Lean compiler and runtime, not just the kernel. Reported separately from `decide`.

A statement proved only for a finite range is never described as proved in general.

## 4. Blind rediscovery protocol (pre-registration)

To make the 4×n Chomp rediscovery test meaningful:

1. Miners and their configs are developed using synthetic data and games *other than* 4×n Chomp.
2. Before any run on Chomp data, the miner code and config are frozen under a git tag (`rediscovery-frozen`).
3. Only after the tag exists does the author add the ground-truth conjectures (`experiments/rediscovery/ground_truth.md`) to the repository.
4. The pipeline's output is scored against the ground truth as **found / partially found / missed / wrong**, and the report quotes the raw output.

The git history shows the order of the tag and the ground-truth commit, so anyone can check the protocol was followed.

**LLM contamination caveat.** If the author's results are public (paper, OEIS A395126), a pretrained LLM may have seen them. LLM-proposed rediscoveries are therefore reported separately from classical-miner rediscoveries, and only the latter count as blind.

## 5. Reproducibility

Every experiment runs from one command and one config file, e.g. `overthink run experiments/configs/<name>.yaml`. Datasets are content-hashed, and run outputs record the exact command, config, git SHA and seed.

## 6. Reporting

`docs/results_log.md` is the source of truth. It records failures as well as successes. Grant and paper text may only cite numbers that appear in the log or in a committed artifact.
